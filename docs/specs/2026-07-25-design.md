# DukaSmart — Design Decisions (v1.1, revised after Codex review R1, 2026-07-25)

Companion to `2026-07-25-requirements.md`. The requirements fix the *what*; this fixes the
*how* where the spec left it open. v1.1 incorporates all 9 required changes from Codex
review round 1 (gpt-5.6-sol, xhigh).

## D1. Location & build strategy
- Project: `~/Documents/Flutter/dukasmart`, git from the start (`main` branch).
- Build order (**Approach A**, approved by Ian; tracks rebalanced per Codex):
  1. **Foundation (serial)** — owns and FREEZES the entire data + app layer (see D9).
  2. **Four parallel feature tracks (Sonnet executors, worktree-isolated)** — screens only:
     - **T1 Products/Inventory:** Product List, Add Product, Add Stock, Low Stock
     - **T2 Sales:** New Sale (POS), Cart UI + cart Notifier (feature-local), Payment, Sale Success
     - **T3 Expenses + Dashboard UI:** Expense List, Record Expense, Home Dashboard (renders
       Foundation's `DailyMetrics` stream — no new aggregates)
     - **T4 Daily Close:** Close Day, Daily Report, rule-based insight generator
       (feature-local pure Dart)
  3. **Integration (serial):** wiring check, validation pass, reviews, acceptance test, APK.
- Folder structure per requirements §"Project structure".

## D2. Money = integer cents (exact rules)
- All monetary DB columns are `int` cents. **`double * 100` is banned everywhere.**
- Input parsing: numeric text fields accept digits with optional `.` and ≤2 decimals;
  parsed as string → `int` cents (`"55.5"` → 5550; `"55"` → 5500). Reject anything else.
- Formatting: `MoneyText` is the only amount renderer. `KES 12,450` when cents are zero;
  `KES 12,450.50` otherwise (intl `NumberFormat`).
- Quantities are `int` units. Line total = `sellingPriceSnapshot × quantity` (int math).
  All aggregates are integer sums of stored values — never recomputed from doubles.

## D3. Data layer (all implemented and frozen by Foundation)
- Drift schema: exactly the six mandated tables. Prices (`buyingPrice`, `sellingPrice`)
  are **nullable** — the dashboard's Attention Needed list flags null prices, per spec.
- **Day boundary rule:** every "today"/daily query uses half-open local-time bounds:
  `createdAt >= startOfLocalDay && createdAt < startOfNextLocalDay`. The Record Expense
  form's selected date SETS the expense's `createdAt` (at 12:00 local, so it lands inside
  the chosen day); default is now.
- **Atomic DAO contracts** (each a single Drift transaction; validation inside the tx):
  - `ProductsDao.createProduct(p, openingQty)` — insert product; if `openingQty > 0`
    insert `openingStock` movement (+qty). Duplicate non-empty barcode → error.
  - `StockDao.receiveStock(productId, qty, newBuyingPrice?, note?)` — require `qty > 0`;
    increment product qty; update buyingPrice if provided; insert `stockReceived`
    movement (+qty).
  - `SalesDao.completeSale(lines, payment)` — aggregate lines by product; for each,
    re-check `stock >= qty` inside the tx (any failure aborts the whole sale); insert
    sale, sale_items with `buyingPriceSnapshot = product.buyingPrice ?? 0` and
    `sellingPriceSnapshot`; decrement stock; insert `sale` movements (−qty,
    `referenceId = saleId`). Returns `saleId`.
  - `DailyCloseDao.closeDay(date, actualCashCents, note?)` — recompute every aggregate
    from source tables inside the tx and **upsert by date** (re-closing a day replaces
    that day's record with fresh figures).
- **Movement sign convention:** `openingStock`/`stockReceived` positive;
  `sale` negative; `manualCorrection` signed. Stock is never allowed below zero.
- **Double-submit protection:** every mutating screen's submit button is state-guarded
  (disabled while an async submit is in flight, via its Riverpod notifier). The POS
  checkout additionally clears the cart only after `completeSale` returns.
- **Seeding = true first-run:** performed in the database's `MigrationStrategy.onCreate`
  (runs exactly once, when the DB file is first created — not "table is empty").
  Seeds the 5 demo products AND an `openingStock` movement for each, honoring
  "every stock change creates a movement."
- UI reads via Drift watch queries wrapped in Riverpod `StreamProvider`s.
- **`DailyMetrics` read-model lives in Foundation** (single authoritative implementation,
  used by Dashboard, Close Day, and Daily Report): totalSales, cashSales, mpesaSales,
  expensesTotal, cashExpenses, cogs, grossProfit, netResult, txCount, lowStockCount,
  attention lists, best-seller.

## D4. Authoritative formulas (int cents; all filtered by D3 day bounds)
- `totalSales = Σ sales.total`; `cashSales`/`mpesaSales` split by `paymentMethod`.
- `cogs = Σ sale_items(buyingPriceSnapshot × quantity)` for the day's sales.
- `grossProfit = totalSales − cogs`
- `expensesTotal = Σ expenses.amount`; `cashExpenses` = cash-method subset.
- `netResult = grossProfit − expensesTotal`
- `expectedCash = cashSales − cashExpenses`; `cashDifference = actualCash − expectedCash`
- `txCount = count(sales)`
- **Best-seller:** highest Σ quantity across the day's sale_items; tie → higher revenue
  (Σ total); still tied → alphabetical first. No sales → none (report says
  "No sales recorded").
- **Insight generator (deterministic templates):** always states total sales; adds M-PESA
  share sentence when `totalSales > 0`; best-seller sentence when one exists; low-stock
  sentence when `lowStockCount > 0`; cash short/over sentence when `cashDifference ≠ 0`.
- **Daily Report** renders the STORED `daily_closes` row for the date (not live data),
  labeled "as at close" — activity after closing is picked up by re-closing (D3 upsert).
  App never locks after close.

## D5. Edge-case rulings (within the fixed 13 screens — no new screens)
- **"View Sale"** (Sale Success) → bottom sheet listing the completed sale's items,
  quantities, and totals.
- **"View Product"** (Low Stock) → bottom sheet with product details + Add Stock action.
- Products with **null selling price cannot be added to the cart** (tile disabled with
  explanatory snackbar). Null buying price sells fine but snapshots cost 0 and is flagged
  in Attention Needed. Zero is a valid (non-flagged) price; empty input = null.
- **Barcode:** unique when non-empty (duplicate → validation error on save). POS scan
  with no match → "Product not found" snackbar.
- Stock statuses: `qty == 0` Out of Stock; else `qty <= threshold` Low Stock; else In Stock.

## D6. Navigation & central-file ownership
- GoRouter `StatefulShellRoute.indexedStack`, 4 tabs (Home, Sell, Products, Expenses);
  Add Stock / Low Stock / Close Day / Daily Report pushed from Home.
- **Foundation registers ALL routes up-front**, pointing at stub screen files inside each
  feature folder. Tracks implement their own stub files; **no track ever edits the
  router, `lib/app/*`, `lib/core/*`, generated `*.g.dart`, or root providers.** Splash
  screen is Foundation-owned. Serial integration alone touches central wiring thereafter.
- Cart is a Riverpod `Notifier` inside `features/sales/` (T2-owned, in-memory only).

## D7. Platform plan (dev on web, release on Android)
- **Drift web is explicit, not automatic:** pin `sqlite3.wasm` + `drift_worker.js`
  versions matching the drift release, placed in `web/`, wired per the official Drift web
  setup. `drift_flutter` selects native SQLite (via `sqlite3_flutter_libs`) on Android.
  Chrome is a time-boxed dev aid only.
- **Mandatory Android acceptance run before the release APK** — physical device via adb
  preferred; if none is connected at integration time, flag to Ian before downloading an
  emulator system image (~1GB).
- **Scanner fallback:** POS and Add Product always show manual barcode text entry;
  `mobile_scanner` wrapped in try/catch — camera errors degrade to manual entry.
- **Images:** picked images are copied into `getApplicationDocumentsDirectory()` and that
  durable path is stored — never the picker's temp path. On web, images are skipped
  (imagePath stays null; UI hides the option).

## D8. Validation, errors, empty states
- Form validators enforce all business rules (non-negative prices, cash ≥ total, M-PESA
  amount == total, expense > 0, required fields). DAO transactions are the backstop.
- Every list has an EmptyState; failed saves surface as snackbars.

## D9. Interface freeze (the parallel-safety contract)
Before any track branches, Foundation commits and freezes: the schema + generated Drift
output, all DAO signatures and implementations, `DailyMetrics` DTO + providers, route
names/paths + stub screens, enums (units, payment methods, expense categories, movement
types), movement sign conventions, money parsing/formatting helpers, and shared widgets.
Tracks add files only under their own `lib/features/<x>/` directory.

## D10. Testing (deliberately minimal)
Unit tests only where arithmetic can silently lie: money parsing/formatting, close-day
math (D4 formulas incl. tie-breaks), `completeSale` stock reduction + abort-on-shortage,
day-boundary filtering. No widget-test suite — one-day scope.

## D11. Review & delivery
Each track gets an independent Sonnet xhigh review. Integration then runs the full
acceptance flow (Chrome + the mandatory Android run), `flutter build apk --release`,
README with run/build instructions.
